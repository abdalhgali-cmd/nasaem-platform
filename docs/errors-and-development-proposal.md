# تقرير الأخطاء ومقترح التطوير — منصة نسائم الحرمين (Nasaem Platform)

> تاريخ الإعداد: 2026-08-04
> نطاق المراجعة: المستودع الكامل (backend + frontend + إعدادات Docker) اعتمادًا على الفرع `main` حتى الالتزام `17e11a0`.

---

## 1. ملخص تنفيذي

تمت مراجعة كامل الكود المصدري للمنصة (باك-إند Node.js/Express + Prisma + PostgreSQL، وواجهة أمامية شبه معدومة). المشروع في مرحلة تأسيسية (Bootstrap) ويحتوي على بنية باك-إند جيدة التنظيم (Modules منفصلة لكل كيان)، لكن توجد أخطاء حرجة تمنع تشغيل النظام من الأساس، بالإضافة إلى ثغرات منطقية في حسابات الدفع، وفجوات كبيرة في الوظائف الأساسية (لا يوجد Frontend فعلي، ولا رفع ملفات حقيقي، ولا تعديل/حذف للبيانات).

تم تصنيف الأخطاء حسب الخطورة، يليها مقترح تطوير مرحلي.

## 3. مقترح التطوير

### المرحلة 1 — إصلاحات عاجلة (لتشغيل النظام أصلًا)

1. **توليد وحفظ Migrations فعلية**: تشغيل `npx prisma migrate dev --name init` محليًا لإنشاء أول Migration، والتزامها (commit) داخل `backend/prisma/migrations/`، ثم تعديل أمر تشغيل الحاوية في `docker-compose.yml` إلى:
   `sh -c "npx prisma migrate deploy && npm run dev"`
   (وليس `prisma generate` فقط).
2. **تصحيح `DATABASE_URL` الافتراضي** في `.env.example` ليستخدم `postgres` (اسم الخدمة) بدل `localhost` عند التشغيل عبر Docker Compose، مع توضيح الفرق في `README.md` بين التشغيل المحلي والتشغيل داخل Docker.
3. **توثيق خطوة إنشاء `.env`** بوضوح في `README.md` (نسخ `.env.example` إلى `.env` وتعديل القيم)، أو إضافة سكربت `setup.sh` يقوم بذلك تلقائيًا.
4. **إضافة `healthcheck`** لخدمة `postgres` في `docker-compose.yml` مع `depends_on: condition: service_healthy` لضمان جاهزية قاعدة البيانات قبل بدء الباك-إند.
5. **البدء الفعلي في بناء الواجهة الأمامية** (`request.html`, `admin-dashboard.html` والأصول المرتبطة بها) بما يتوافق مع بيانات `services-data.js` الموجودة فعلًا، أو توضيح خطة تقنية بديلة (React/Vue SPA) إذا كان هذا هو الاتجاه المطلوب.

### المرحلة 2 — إصلاح المنطق والموثوقية

6. استبدال توليد الأرقام التسلسلية القائم على `count()` بحل ذري (Atomic)، إما عبر:
   - عدّاد مخصص في جدول `Setting` يُحدَّث ضمن Transaction بقفل صفوف (`SELECT ... FOR UPDATE`)، أو
   - تسلسل قاعدة بيانات (Postgres `SEQUENCE`) يُستدعى داخل نفس الـ Transaction.
7. إعادة كتابة `recalculateOrderPaymentStatus` لاستبعاد الدفعات ذات الحالة `REFUNDED` (وربما `UNPAID`) من مجموع المبلغ المدفوع، مع إضافة اختبارات تغطي حالات الاسترجاع الجزئي والكلي.
8. تعريف آلة حالات صريحة (State Machine) للطلبات — خريطة انتقالات مسموحة فقط (مثال: `NEW → UNDER_REVIEW → ... → COMPLETED`، ومنع الرجوع لحالات سابقة إلا بصلاحية خاصة) والتحقق منها في `updateOrderStatus` قبل التنفيذ.
9. حذف أحد ملفي `requireRole` المكررين (`role.middleware.js` أو الدالة داخل `auth.middleware.js`) والاكتفاء بمصدر واحد يُستورد في كل الوحدات.
10. تفعيل رفع ملفات حقيقي عبر `multer` (الموجودة أصلًا في `package.json`) مع تخزين محلي مؤقت أو تكامل مع تخزين سحابي (S3-compatible)، والتحقق من نوع/حجم الملف قبل القبول، وربط `documents.controller.js` بهذه الآلية بدل قبول `storagePath` كنص حر من العميل.
11. إضافة Rate Limiting مخصص وأكثر صرامة على `/api/auth/login` (مثلًا 5-10 محاولات لكل 15 دقيقة لكل IP/بريد إلكتروني).

### المرحلة 3 — اكتمال الوظائف الأساسية

12. إضافة عمليات تعديل وحذف (Update/Delete أو Soft-Delete عبر حقل `deletedAt`) لجميع الكيانات الرئيسية (العملاء، الفروع، الموردين، المستندات، العروض، الخدمات).
13. إضافة ترقيم صفحات (`page`/`limit`) وفلاتر بحث لكل نقاط النهاية التي تُرجع قوائم، مع تقليل حجم `include` الافتراضي (جلب التفاصيل الكاملة فقط عند طلب سجل واحد).
14. تحويل حقلي `priority` و`currency` إلى قيم مُقيَّدة (Enum على مستوى Prisma، أو ربط `currency` فعليًا بجدول `Currency` الموجود مسبقًا) بدل نصوص حرة.
15. مزامنة مدة صلاحية كوكي المصادقة مع `JWT_EXPIRES_IN` بدل قيمة ثابتة، وإضافة نقطة نهاية `POST /api/auth/logout` لمسح الكوكي.
16. قراءة كلمة مرور المسؤول الافتراضي في `seed.js` من متغير بيئة (`SEED_ADMIN_PASSWORD`) بدل تثبيتها في الكود، مع فرض تغييرها عند أول تسجيل دخول.
17. تفعيل نموذجي `ActivityLog` و`Notification` فعليًا: تسجيل كل عملية حساسة (تسجيل دخول، إنشاء/تعديل طلب، تغيير حالة دفع) في `ActivityLog`، وإرسال إشعارات داخلية عند أحداث مهمة (تغيير حالة الطلب، استلام دفعة).

### المرحلة 4 — تحسينات إضافية مقترحة للنمو المستقبلي

18. إضافة اختبارات آلية (Unit/Integration Tests) — لا يوجد حاليًا أي مجلد اختبارات في المشروع، ما يجعل أي تعديل مستقبلي عرضة لكسر السلوك الحالي دون اكتشاف مبكر.
19. إضافة إعداد CI (مثل GitHub Actions) يُشغّل `npm install`، فحص الأنماط (Lint)، والاختبارات تلقائيًا عند كل Pull Request.
20. توثيق واجهة الـ API (OpenAPI/Swagger) لتسهيل التكامل مع الواجهة الأمامية القادمة ولتوضيح العقود بين الطرفين.
21. إضافة تقارير مالية ولوحة تحكم أكثر تفصيلاً (إجمالي الإيرادات، المتأخرات، تقارير حسب الفرع/الموظف) بدل الإحصاءات الأساسية الحالية (عدّادات فقط) في `dashboard.service.js`.
