## 2. تطبيق أندرويد للاختبار على جهاز حقيقي

**الملف:**

**الرابط:**
- صفحة البناء: https://github.com/abdalhgali-cmd/nasaem-platform/actions/runs/41255293960
- انزل إلى قسم **Artifacts** في أسفل الصفحة. يتطلب ذلك تسجيل الدخول إلى GitHub بحساب له صلاحية على المستودع.

**خصائص هذه النسخة:**
- موقّعة بمفتاح الاختبار الثابت، فتُثبَّت فوق أي نسخة تجريبية سابقة دون حذفها.
- تتصل بخادم **Staging** فقط: `adaptable-quietude-staging.up.railway.app`، وتظهر عليها شارة «بيئة اختبار».
- للاختبار فقط، وليست للتوزيع على العملاء.

**خطوات التثبيت:**
1. حمّل الملف المضغوط من Artifacts، ثم فك ضغطه لتحصل على ملف `.apk`.
2. انقل الملف إلى الهاتف عبر واتساب أو Google Drive أو كابل USB، أو حمّله مباشرة من المتصفح على الهاتف.
3. افتح الملف على الهاتف. عند ظهور رسالة «مصدر غير معروف»، اسمح للتطبيق الذي فتحت منه الملف بالتثبيت: الإعدادات ← الأمان أو التطبيقات ← تثبيت التطبيقات غير المعروفة.
4. اضغط «تثبيت»، ثم افتح التطبيق، وتأكد من ظهور شارة «بيئة اختبار».
5. نفّذ القسم 2 من `docs/release/MANUAL-TEST-CHECKLIST-ar.md`.

**مهم:** لكي يعمل التطبيق بالكامل، يجب أن يعمل على Staging إصدار من الخادم يحتوي هذه الـPRs، وأن تكون الأسعار والحسابات مضبوطة (البند 5). اختبار التطبيق على Staging الحالي يختبر الإصدار المنشور هناك الآن، لا الكود الجديد.

## 3. Staging: الإتاحة، والنسخة الاحتياطية، وتجربة الاسترجاع

**الإتاحة:** لم أستطع الوصول إلى Staging من هذه البيئة. سياسة الشبكة تحجب `adaptable-quietude-staging.up.railway.app` (وكذلك `railway.com` و`docs.railway.com` و`vercel.com`). لذلك لم يُقرأ ولم يُكتب أي شيء على Staging. لإتاحة ذلك: إعدادات البيئة ← Network access ← Allowed domains.

**ما تم فعليًا (بأمان، محليًا):**
- **تجربة كاملة لأداة الاسترجاع** `scripts/release-restore-drill.sh` على نسخة من قاعدة اختبار محلية، مع أرشيف مجلد المستندات:
  - النتيجة: **نجاح (exit 0)**.
  - الاسترجاع تم في قاعدة جديدة منفصلة.
  - الترحيلات: 65، ولا ترحيل معلّق.
  - ملفات المستندات المفقودة: 0.
  - فحص الرجوع للإصدار السابق: آمن.
  - حُذفت قواعد التجربة بعد الانتهاء.
- **حماية الأداة:**
  - ترفض أي خادم قاعدة بيانات غير محلي.
  - لا تكتب إلا في قاعدة جديدة تنشئها بنفسها.
  - **لا تلمس Staging ولا الإنتاج.**

**ما يجب أن تنفّذه أنت على Staging** (الخطوات التفصيلية في `docs/RELEASE-91-RAILWAY-RUNBOOK.md` §2–3):
1. **لقطة Railway:** Railway ← بيئة staging ← خدمة قاعدة البيانات ← Backups ← نسخة يدوية. اللقطة وحدها لا تكفي.
2. **نسخة خارجية من قاعدة البيانات** بأداة إصدارها 18 أو أحدث:
   ```
   pg_dump -Fc --no-owner --no-acl "<DATABASE_URL الخاص بـstaging>" > nasaem-staging-$(date +%F).dump
   ```
   القيمة تُنسخ من Railway ← Postgres ← Variables، ولا تُكتب في أي ملف أو محادثة.
3. **أرشيف المستندات** من الخدمة:
   ```
   tar czf uploads-$(date +%F).tar.gz -C /data uploads
   ```
4. **تجربة الاسترجاع** على جهازك، مع قاعدة PostgreSQL محلية:
   ```
   DRILL_ADMIN_URL=postgresql://postgres:<pw>@localhost:5432/postgres ROLLBACK_REF=<commit المنشور الآن على staging> DRILL_EXPECT_ROLLBACK_EXIT=0 scripts/release-restore-drill.sh nasaem-staging-<date>.dump uploads-<date>.tar.gz
   ```
   - يجب أن تنتهي بـ`"pass": true`.
   - `DRILL_EXPECT_ROLLBACK_EXIT=0` صحيح إذا كان Staging يعمل على الفرع الأساسي (لا ترحيلات جديدة). إذا كان يعمل على إصدار أقدم، تُترك القيمة الافتراضية 2.
5. احفظ النسختين خارج Railway، في مكان مشفّر.

## 4. استضافة المنصة كاملة على Railway — التكوين والتكلفة التقديرية

**التكوين المقترح:** مشروع واحد `spirited-luck` يضم بيئتين، staging وproduction. كل بيئة فيها:

| الخدمة | الوصف | ملاحظات |
|---|---|---|
| `api` | الخادم (Dockerfile الموجود)، ومعه لوحة الإدارة القديمة | مجلد دائم `/data/uploads`، و`UPLOAD_ROOT=/data/uploads` |
| `web` | الموقع ولوحة الإدارة الجديدة (Next.js) | البناء `npm run build`، والتشغيل `npm start`، والمجلد `web/`، والمتغير `NEXT_PUBLIC_API_URL` |
| `Postgres` | قاعدة البيانات | مع مجلد دائم ونسخ احتياطية |

**الأسعار الرسمية من Railway (تحقق منها قبل الالتزام):**
- خطة Pro: ‏20$ شهريًا لكل عضو، وتشمل 20$ من الاستهلاك.
- المعالج: 20$ لكل vCPU شهريًا.
- الذاكرة: 10$ لكل GB شهريًا.
- التخزين: 0.15$ لكل GB شهريًا.
- نقل البيانات للخارج: 0.05$ لكل GB.
- الفوترة حسب الاستهلاك الفعلي بالثانية، لا حسب الحد الأقصى.

**تقدير الاستهلاك:** تقدير تقريبي لحركة إطلاق أولي محدودة، وليس قياسًا.

| البند (بيئة الإنتاج) | الاستهلاك المتوسط المفترض | التكلفة الشهرية التقريبية |
|---|---|---|
| api | ‏0.1 vCPU + ذاكرة 0.5GB | ‏≈ 7$ |
| web | ‏0.1 vCPU + ذاكرة 0.5GB | ‏≈ 7$ |
| Postgres | ‏0.05 vCPU + ذاكرة 0.3GB + تخزين 5GB | ‏≈ 5$ |
| مجلد المستندات | ‏20GB | ‏≈ 3$ |
| نقل البيانات | ‏30GB | ‏≈ 1.5$ |
| **المجموع لبيئة الإنتاج** | | **≈ 20–25$** |
| بيئة staging (استهلاك أقل) | | ‏≈ 8–15$ |

**الإجمالي التقديري:**
- اشتراك Pro ‏20$ (عضو واحد) يغطي أول 20$ من الاستهلاك.
- لذلك الإجمالي الشهري نحو **35–45$** لبيئتين.
- قد يرتفع مع زيادة الطلبات، أو حجم الملفات، أو إضافة أعضاء للفريق (20$ لكل عضو إضافي).
- يمكن وضع حد أعلى للإنفاق من إعدادات Railway.

**لماذا Railway:**
- الخادم وقاعدة البيانات يعملان عليه أصلًا.
- الموقع Next.js عادي لا يعتمد على Vercel.
- مزود واحد، وفاتورة واحدة، والاتصال بين الخدمات داخلي.

## 6. إعدادات واتساب والبريد (فحص دون كشف أي سر)

| القناة | المتغيرات | ماذا يحدث بدونها |
|---|---|---|
| واتساب: رمز تتبع الطلب | `WHATSAPP_API_TOKEN` و`WHATSAPP_PHONE_NUMBER_ID` | **عائق:** لا يصل الرمز، فلا يستطيع العميل فتح «طلباتي» ومتابعة طلبه. يظهر له: «إرسال رمز التحقق عبر واتساب غير متاح حاليًا» |
| واتساب: إشعار خارج نافذة 24 ساعة | `WHATSAPP_TEMPLATE_NAME` (قالب معتمد من Meta) | الرسائل الحرة لا تصل إلا لمن راسل الرقم خلال 24 ساعة |
| واتساب: إشعار الإدارة | `WHATSAPP_ADMIN_NUMBER` | لا يصل إشعار الطلبات الجديدة للإدارة عبر واتساب. الإشعارات داخل اللوحة تعمل |
| البريد: إيصال السداد وتأكيد الطلب | `PROVIDER_EMAIL_API_URL` و`PROVIDER_EMAIL_API_KEY` | لا يُرسل البريد. يُسجَّل «خدمة البريد غير مهيأة»، والإيصال يبقى قابلًا للتحميل من الطلب. لا يُدَّعى أبدًا أن رسالة وصلت دون أن تُرسل |

**الأمان:**
- لا تُطبع القيم السرية في أي سجل أو تقرير.
- وضع «capture» لاختبار البريد يُتجاهل تلقائيًا في الإنتاج.

**أداة فحص الجاهزية (جديدة، للقراءة فقط، ضمن #152):**
```
npm run release:readiness          # ملخص عربي بالعوائق والتنبيهات
npm run release:readiness -- --json
```
- **طريقة التشغيل:** من Railway ← خدمة api ← Shell.
- **ما تعرضه:**
  - وجود كل متغير أو غيابه، دون قيمته.
  - مجلد المستندات: موجود وقابل للكتابة، دون أن تكتب فيه شيئًا.
  - عدد الترحيلات المطبّقة.
  - أسعار العمرة ومصر الفعلية.
  - أسعار الصرف المفعّلة.
  - حسابات الاستلام لكل عملة.
  - عدد الموظفين لكل دور.
  - الخصائص المعطّلة.
- **ما لا تفعله:** لا تكتب شيئًا في قاعدة البيانات أو القرص.
- **كيف تُقرأ نتيجتها:** تنتهي برمز 1 إذا وُجد عائق.
- **الاختبار:** اختبار آلي يتأكد أن القيم السرية لا تظهر أبدًا في المخرجات (2/2). جرّبتها محليًا على قاعدة جديدة، فاكتشفت العوائق الصحيحة: الأسعار غير مضبوطة، وواتساب، والبريد، ولا يوجد موظف عمليات.

2. لم يُختبر التطبيق على جهاز حقيقي.
3. واتساب: لم يُؤكَّد ضبطه. بدونه لا يستطيع العملاء متابعة طلباتهم.
4. الأسعار على Staging: لم يُؤكَّد ضبطها، وسعر صرف الريال غير مقرر.
5. حساب Vercel موقوف، والبديل الموصى به Railway.

### 🟡 قرارات تحتاج موافقتك
1. تنفيذ خطة الدمج (البند 1)، ثم PR إصدار واحد إلى `main`.
2. تنفيذ النسخة الاحتياطية والاسترجاع على Staging بنفسك، أو إتاحة النطاقات لهذه البيئة.
3. نشر الإصدار الجديد على Staging بعد نجاح الاسترجاع.
4. تأكيد أسعار مصر (85 / 155 USD، صرف 9200).
5. تحديد سعر صرف الريال إلى الجنيه.
6. إيقاف باقتي العمرة القديمتين أو إبقاؤهما.
7. اختيار مزود البريد، وتفعيل حساب واتساب للأعمال وقالب معتمد.
8. اعتماد Railway للموقع، أو الترقية إلى Vercel Pro.
9. توزيع نسخة الإنتاج من التطبيق (لاحقًا، بعد اجتياز الاختبار على جهاز حقيقي).
