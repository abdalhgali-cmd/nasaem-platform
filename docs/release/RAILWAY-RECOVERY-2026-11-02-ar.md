## 2. فشل نشر `reasonable-connection`

**السبب:** تشخيص Railway يقول إن `DATABASE_URL` يُحلّ إلى نص فارغ. الأرجح أنه مرجع من نوع `${{<اسم خدمة>.DATABASE_URL}}` إلى خدمة PostgreSQL غير موجودة في هذا المشروع أو بهذا الاسم. Prisma يفشل حينها بالخطأ P1012، ثم يفشل فحص الصحة.

**ملاحظات:**
- هذا المشروع ليس بيئة Staging المعتمدة. المعتمدة هي `spirited-luck / staging`.
- اسمه `production`، لكنه يتابع `main` باسم خدمة «staging».

**ما أُعدّ في الكود (الفرع `fix/railway-recovery-20261102`):**
- السكربت `backend/src/scripts/check-database-url.js` يعمل قبل `prisma migrate deploy` (في `backend/Dockerfile`).
- يرفض بدء الحاوية، **دون تشغيل أي ترحيل**، في هذه الحالات:
  - `DATABASE_URL` فارغ؛
  - الرابط غير صالح؛
  - الرابط ليس PostgreSQL؛
  - الرابط لا يطابق `EXPECTED_DATABASE_HOST` أو `EXPECTED_DATABASE_NAME` إن ضُبطا.
- يطبع رسالة تذكر طريقة الإصلاح.
- لا يطبع إلا المضيف والمنفذ واسم القاعدة، ولا يطبع اسم المستخدم أو كلمة المرور أبدًا.

**قرار المالك، وأحد الخيارين:**
- **(أ) موصى به: إيقاف هذا المشروع إن لم يكن له استخدام.** من Settings ← Source افصل الربط مع GitHub، أو احذف الخدمة. بهذا يتوقف النشر الفاشل من `main`.
- **(ب) إن كان مطلوبًا:**
  1. أضف خدمة PostgreSQL **داخل المشروع نفسه**.
  2. اجعل `DATABASE_URL` على `nasaem-platform-staging` مرجعًا إليها: Variables ← Add reference.
  3. اضبط `EXPECTED_DATABASE_HOST` واسم القاعدة.
- **تحذير:** لا تلصق رابط قاعدة الإنتاج في هذا المشروع أبدًا. وإلا ستُشغَّل الترحيلات على الإنتاج من خدمة «staging».

**التحقق دون كشف الأسرار:** اسم خدمة PostgreSQL في `spirited-luck / staging` هو `Postgres-_h_s` حسب `docs/RELEASE-91-RAILWAY-RUNBOOK.md`. أي مرجع مكتوب يدويًا بغير هذا الاسم يُحلّ إلى نص فارغ.

## 3. موقع الإنتاج على Railway (يُنفَّذ بموافقتك)

1. في `spirited-luck / production`: New ← GitHub Repo ← نفس المستودع، **Root Directory = `web`**، والفرع `main`.
   - الملف `web/railway.json` يحدد أمر البناء `npm run build`، وأمر التشغيل `npm run start`، وفحص الصحة `/healthz`.
2. متغيرات خدمة الموقع:

   | المتغير | القيمة |
   |---|---|
   | `NEXT_PUBLIC_API_URL` | `https://nasaem-platform-production.up.railway.app/api` |
   | `NEXT_PUBLIC_PRODUCTION_WEB_HOSTS` | نطاق الخدمة على Railway، مثل `nasaem-website-production.up.railway.app` |

   - البناء يتوقف برسالة واضحة إن غاب `NEXT_PUBLIC_API_URL`.
   - المتغير الثاني ضروري: بدونه يرى الموقع نطاقه غير معروف، فيمنع الاتصال بـAPI الإنتاج. هذه حماية مقصودة.
3. في خدمة API الإنتاج:
   - أضف نطاق الموقع الجديد إلى `CORS_ORIGIN`، بالضبط وبصيغة `https://…`.
   - اختياري: `ADMIN_APP_URL` بنفس النطاق، لتحويل صفحات الإدارة القديمة على عنوان الـAPI.
4. اختبر على النطاق `*.up.railway.app`: الرئيسية، ونموذج العمرة، ونموذج مصر، وفتح `/admin` لمركز العمليات.
5. **DNS:** نقل `nasaem-alharamain.com` من Vercel إلى Railway قرار منفصل، ولم يُنفَّذ.

**لوحة الإدارة:** تفتح على `/admin` مباشرة، وهو مركز العمليات. الشاشات القديمة تعمل داخلها وتستخدم عنوان الـAPI نفسه على أي نطاق.

## 4. الأسعار والدفع

- **الإنتاج يعلن الآن أن أسعاره نهائية:** `/api/health` يرد بـ`pricesAreTestData:false`.
- **ما تغيّر في هذا الفرع:**
  - الأسعار تُعدّ بيانات اختبار **حتى في الإنتاج**، إلى أن يُضبط `PRICES_APPROVED=true` على خدمة API الإنتاج.
  - بذلك يظهر شريط «نسخة تجريبية: الأسعار المعروضة للتجربة فقط» للعملاء والموظفين على الموقع.
  - **لا تضبط `PRICES_APPROVED` قبل اعتماد الأسعار.**
- **تطبيق الهاتف لا يعرض هذا الشريط.** يلزم تحديث للتطبيق وتوزيع جديد، وهذا قرار منفصل.
- **الدفع:** التحويل البنكي يدوي، ولا يوجد دفع إلكتروني. لكن حسابات الدفع المفعّلة على الإنتاج تُعرض على العملاء.
  - إن أردت منع أي تحويل حقيقي قبل الاعتماد، أوقف حسابات الدفع على الإنتاج من لوحة الإدارة.
  - هذا تغيير بيانات، ولم يُنفَّذ.
- **الكتالوج:** على الإنتاج باقة واحدة منشورة (`SVC-PKG-FAMILY`، «حسب الطلب»)، ولا توجد باقات عمرة. لم يُغيَّر شيء.
