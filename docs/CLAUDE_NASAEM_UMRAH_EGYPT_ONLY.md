# NASAEM — تنفيذ العمرة والموافقة الأمنية فقط

**الدور:** Senior Full-Stack + UI/UX + Security + QA. **المستودع:** `abdalhgali-cmd/nasaem-platform`.

## النطاق الصارم
- ركّز **حصرياً** على خدمتي **العمرة** و**الموافقة الأمنية المصرية** عبر **الموقع + تطبيق Android + لوحة الإدارة + API**.
- **اترك جميع الخدمات والخيارات الأخرى كما هي تماماً**: لا حذف أو إخفاء أو إعادة تصميم أو تعديل مساراتها أو أسعارها أو سلوكها. لا توسع إلى الطيران/الفنادق/البواخر إلا ربط *طلب تذكرة اختياري* داخل مسار الموافقة القائم، دون تغيير نظام حجز الطيران نفسه.
- أعد استخدام الكود الحالي. حافظ على الطلبات القديمة والتوافق مع نسخ التطبيق المثبتة.

## 00 — تدقيق سريع قبل التعديل
1. اقرأ `CLAUDE.md` ومواضع العمل ذات الصلة في `TASKS.md`، ثم `git status` وآخر فروع/PRs المعنية، خاصة `#128–#139`. تحقق من الأساس المطبق على Staging؛ **لا تعِد تنفيذ إصلاح موجود**.
2. افحص مسار الخدمتين فقط في الواجهات وAPI وقاعدة البيانات والاختبارات: **اختيار ← رفع المستندات ← تأكيد السعر ← دفع/إيصال ← مراجعة موظف ← تنفيذ ← تسليم/تتبع**.
3. سجّل النواقص الحقيقية مع ملف/سطر ودليل، ورتّبها `P0/P1/P2`. لا تفحص المستودع كاملاً مرة أخرى ولا تنسخ تقارير قديمة.

## 01 — العمرة
- **3 أنواع:** تأشيرة فقط، خدمات بالطيران، خدمات بالبحر. أظهر **السعر المنشور الفعلي** بالريال والجنيه من الخادم، ولا تخترع أسعاراً أو تحوّله إلى «طلب عرض سعر».
- النموذج المختصر: اسم مقدم الطلب، **جوازات جميع المعتمرين**، **إقامة الضامن**، **رقم هاتف الضامن إلزامي**، رقم إضافي اختياري.
- اعرض المبلغ النهائي وحساب التحويل وزر نسخ الرقم؛ تصوير/رفع **إيصال صورة أو PDF**، أو «سأحوّل لاحقاً». الرفع = **تحت المراجعة** وليس دفعاً مؤكداً.
- بعد اعتماد المحاسب: **جاري إصدار التأشيرة** (تأشيرة فقط) أو **جاري إصدار التذاكر** (مع الخدمات)، ثم رفع الملفات النهائية لكل معتمر، تنزيلها وتتبع المراحل.
- اختصر النصوص، وأزل أي مرحلة عرض سعر لهذه الباقات ذات السعر الثابت، مع الحفاظ على معلومات المشتملات والاستثناءات.

## 02 — الموافقة الأمنية المصرية
- خياران: **جوي / بري (حربي)**، بسعر ثابت `USD + SDG` **من إعدادات الخادم**؛ لا تثبّت أرقام الأسعار أو سعر الصرف داخل الواجهة. **لا مرحلة عرض سعر**.
- الجوي: جهة القدوم «بورتسودان» والوصول «مطار القاهرة» كقيم افتراضية قابلة للتعديل؛ البري: «منفذ الدخول». لا تسأل طريقة الدخول مرتين.
- تصوير/رفع الجوازات مع معاينة وفحص النوع والوضوح دون رفض غير مبرر؛ تأكيد السعر ثم التحويل ورفع الإيصال ومراجعة المحاسب.
- **إصدار الموافقة وتسليمها أولاً**. بعد ذلك: **طلب تذكرة من الوكالة اختياري** للجوي، ثم تفاصيل الرحلة/تاريخ السفر أو موعد الوصول للمعبر، ثم **إصدار التعميم PDF** وتسليمه. التذكرة ليست شرطاً للموافقة.
- لوحة الإدارة: قائمة مرتبة بتاريخ السفر، موظف مسؤول، حالة الدفع، الإجراء التالي، تنبيه اقتراب السفر، روابط المستندات، صلاحيات وسجل تدقيق. لا يغلق الطلب قبل إكمال المستندات المطلوبة لكل مسافر والتعميم وفق السياسة.

## 03 — الجودة والأمن والتطابق
- **نفس الأسعار والحالات والخطوات** في الموقع والتطبيق ولوحة الإدارة؛ كل الصلاحيات والتحقق من السعر على **الخادم**.
- اختبر: ضيف/مسجل، عدة جوازات، ملف خاطئ، كاميرا/معرض/PDF، انقطاع الإنترنت، حفظ المسودة، تكرار الإرسال، تغير السعر `409`، رفض الإيصال وإعادة الرفع، تسليم/تنزيل الملفات، روابط الإشعارات، منع وصول عميل لملفات غيره، Android حقيقي إن توفر.
- حافظ على CORS/CSRF وRBAC، وأمّن الملفات الحساسة، ولا تسجّل بيانات الجواز في Logs. ميّز الاختبارات الآلية عن التحقق الفعلي على الجهاز وStaging.

## 04 — التنفيذ بكفاءة توكن
- ابدأ **بملخص تدقيق لا يزيد عن 15 سطراً**: `موجود / ناقص / خطر / أول إصلاح`. ثم نفّذ إصلاحات `P0` المؤكدة مباشرة على **فرع جديد** مع اختبارات مستهدفة؛ لا تعِد بناء النظام.
- اقرأ الملفات المتعلقة بالمشكلة فقط؛ لا تطبع ملفات كبيرة أو logs كاملة؛ استخدم بحثاً محدداً. اختبارات مستهدفة أولاً، وCI كامل عند تحضير PR فقط.
- أخرج **PR صغيراً لكل حزمة مترابطة**، واطلب مراجعة Codex قراءة فقط إن كان متاحاً. تحديث مختصر دائماً: `DONE | TESTED | BLOCKED | NEXT` مع المسارات/روابط الأدلة.
- **ممنوع** دمج `main`، النشر إلى Staging/Production، تشغيل ترحيلات على قواعد حية، تعديل أسعار/بيانات العملاء الحية، أو توزيع APK **دون موافقتي الصريحة**. لا تزل الخدمات الأخرى ولا تلمسها؛ إن استلزم إصلاح مشترك تغييراً قد يؤثر عليها، وثّق الأثر واطلب موافقة قبل تنفيذه.

**معيار الإكمال:** اختبار متكامل لكل نوع عمرة ولكل نوع موافقة، من تقديم العميل إلى الدفع والمراجعة والتنفيذ والتسليم والتنزيل، مع ظهور الخطوة نفسها بشكل صحيح في الأنظمة الثلاثة. إذا لم يتحقق اختبار حي أو جهاز فعلي فاكتب `NOT VERIFIED`، لا `DONE`.
