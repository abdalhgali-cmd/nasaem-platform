# خطة إكمال مشروع نسائم الحرمين (Nasaem Platform)

> آخر تحديث: بناءً على حالة الفرع `main` عند commit `c1800c5` (29 أغسطس 2026، CI أخضر).
> هذه الوثيقة هي خطة العمل الموحّدة لإغلاق كل الفجوات المتبقية بين الوضع الحالي
> وبين **إطلاق إنتاجي حقيقي وآمن**. تجمع بين: الفجوات البرمجية المُفصح عنها في
> `NASAEM_PLATFORM_3.0_EXECUTION_PLAN.md`، وبوابات الجاهزية في
> `RELEASE_READINESS_REPORT.md` / `PRODUCTION_READINESS_CHECKLIST.md` /
> `STAGING_READINESS_CHECKLIST.md`، والعمل المفتوح على GitHub (PR #27).

ملاحظة: `docs/errors-and-development-proposal.md` وثيقة قديمة (22 أغسطس) تصف حالة
المشروع في مرحلة مبكرة جدًا (قبل وجود migrations، قبل الواجهة، قبل حماية
تسجيل الدخول). كل بند حرج فيها تم التحقق من إصلاحه فعليًا في الكود الحالي
(migrations موجودة، rate limiting على `/login`، `logout` endpoint، توليد أرقام
ذري عبر `nextSequence`، استبعاد `REFUNDED` من حساب حالة الدفع، آلة حالات صريحة
لحالة الطلب `isValidOrderStatusTransition`). **يُنصح بأرشفتها** بدل تركها كمرجع
حالة حالي كي لا تُقرأ خطأً كقائمة عمل مفتوحة.

### A2. إكمال لوحات الإدارة الناقصة (فجوات مُفصح عنها صراحة في كل مرحلة)
هذه ليست أخطاء، بل ميزات API كاملة ومُختبرة بدون واجهة إدارية بعد:

| الوحدة | الموجود | الناقص |
|---|---|---|
| الخدمات (Services) | إنشاء/تفعيل-تعطيل في `frontend/` | حقول الترتيب (`sortOrder`)/الأيقونة/الصورة/المزايا (`features`) — الـ API جاهز (`PATCH /reorder`, `POST /:id/image`) |
| أنواع التأشيرات | جدول CRUD أساسي | محرر شجرة متطلبات التأشيرة (Visa Requirements) |
| العبارات (Ferries) | CRUD للمشغّل (Operator) | إدارة جداول الرحلات (Schedules) |
| بحث/حجز الطيران (الموقع العام) | نتائج البحث الأساسية | عرض شعار شركة الطيران (`airlineLogoKey`) وإكمال المطارات التلقائي في نافذة تأكيد الحجز |
| مركز التهيئة | 7 تبويبات فعلية | تبويب "تفضيلات الإشعارات" (لا يوجد له backend module أصلًا — يحتاج تصميمًا أولًا) |

خطوات:
- [ ] ترتيب حسب الأثر التشغيلي الفعلي (الأرجح: محرر متطلبات التأشيرة ثم جداول العبارات، لأن الموظفين يستخدمونهما يوميًا الآن عبر الـ API مباشرة).
- [ ] لكل بند: واجهة CRUD بسيطة تتبع نفس نمط `admin-management.js` الحالي (RBAC عبر `mgmtCanWrite()`، بلا بيانات وهمية).
- [ ] تحقق حي في متصفح حقيقي بعد كل بند (نفس منهجية المراحل السابقة)، لا اكتفاء بنجاح الاختبارات الخلفية.

### A3. تثبيت ميزة العملات المتعددة (دُمجت اليوم بدون توثيق أدلة كامل)

## المسار B — التحقق الحي في بيئة Staging (فريق QA + DevOps)

**لا يمكن البدء بهذا المسار قبل توفر Backend + PostgreSQL غير إنتاجيين قابلين للكتابة.** هذا هو المُعطِّل الأساسي الحالي لكل بند هنا.

1. [ ] توفير Staging منفصل تمامًا عن الإنتاج: backend قابل للكتابة + قاعدة بيانات PostgreSQL مستقلة + أسرار (secrets) غير إنتاجية.
2. [ ] تنفيذ مصفوفة عزل العملاء الحية (Customer A/B): إنشاء حسابين وهميين، ومحاولة كل مسار (قوائم، ID مباشر، بحث/فلترة، تصدير، رفع/تنزيل ملفات، تعديل) من كل طرف على موارد الآخر. أي وصول غير مصرح = يوقف الإطلاق.
3. [ ] نفس المصفوفة على مستوى المؤسسات (Organization A/B) بعد إكمال الجرد في A4.
4. [ ] تنفيذ مصفوفة RBAC الكاملة (كل دور × كل مسار حساس) يدويًا/آليًا على Staging، وليس فقط عبر اختبارات الوحدة.
5. [ ] تحقق حي من عزل الملفات: رفع مستند بحساب، محاولة الوصول له من حساب آخر عبر تخمين/تعديل معرف الملف.
6. [ ] تحقق بصري (mobile/RTL) على المسارات الرئيسية (Playwright موجود، لكن مطلوب مرور بشري حقيقي حسب `stages-9-14-status.md`، بند "Stage 12/13").
7. [ ] تدقيق إتاحة (Accessibility) شامل: لوحة مفاتيح، aria، تباين ألوان، حركة مخفّضة — غير منفَّذ بعد رغم نجاح البناء.

**خروج المسار**: كل بند أعلاه PASS مع دليل قابل للتدقيق (لقطات، سجلات، لا "افترضنا أنه يعمل").

## المسار C — البنية التحتية والعمليات (DevOps / Infra Owner)

هذه بنود **لا يمكن لأي عامل كود إغلاقها من داخل المستودع وحده** — تحتاج وصولًا فعليًا لـ Railway/Vercel ولوحات مراقبة حقيقية.

1. [ ] **النسخ الاحتياطي**: جدولة تلقائية + تشفير + مدة احتفاظ + تنبيه عند فشل النسخ.
2. [ ] **الاستعادة (Restore drill)**: تنفيذ استعادة فعلية على بيئة معزولة، وقياس RPO/RTO الفعليين وتوثيقهما (وليس تقديرهما).
3. [ ] **المراقبة والتنبيهات**: صحة الـ backend، اتصال قاعدة البيانات، معدل الأخطاء، زمن استجابة الدفع/الرفع — مع وجهات تنبيه فعلية (Slack/Email/PagerDuty) ومالك تشغيلي (on-call) محدد بالاسم.
4. [ ] **خطة التراجع (Rollback)**: الإجراء موثق في `PRODUCTION_RUNBOOK.md`، لكن **لم يُجرَّب فعليًا** — تنفيذ تمرين تراجع كامل (frontend + backend + migration) على بيئة غير إنتاجية.
5. [ ] **الاستجابة للحوادث**: تمرين تشغيلي واحد على الأقل (محاكاة عطل) لاختبار مسار التصعيد والتواصل مع العملاء.
6. [ ] بعد نجاح كل ما سبق فقط: تطبيق Migrations الفعلية على قاعدة بيانات Railway الإنتاجية (باستخدام `prisma migrate deploy` حصرًا، أبدًا `migrate dev`/`db push`).

## المسار D — قرارات العمل والقانون (صاحب المنتج / المالك)

لا حل برمجي لهذه البنود — هي قرارات يجب أن تصل من المالك/الإدارة:

1. [ ] **الدفع**: اعتماد "الدفع اليدوي بالمراجعة" كسياسة رسمية نهائية، أو اختيار بوابة دفع فعلية وتزويد بيانات اعتماد Sandbox حقيقية لاختبارها (webhooks، استرجاع، تسويات).
2. [ ] **الموردون** (فنادق/طيران/تأشيرات خارجية إن وُجدت): تأكيد أي تكامل مفعّل فعليًا واختباره في Sandbox حقيقي، أو اعتماد "تدفق يدوي" رسميًا حيث لا يوجد عقد تكامل.
3. [ ] **الأسعار والباقات**: اعتماد نهائي لأسعار التأشيرات/باقات العمرة/رسوم الخدمات — خاصة بعد إضافة العملات المتعددة اليوم (من يعتمد سعر الصرف؟ كم مرة يُحدَّث؟).
4. [ ] **المحتوى القانوني**: نصوص رسمية معتمدة للخصوصية، الشروط، الإلغاء، الاسترداد، سياسة الدفع، إشعار الوثائق (الموجود حاليًا نصوص placeholder تقنية فقط).
5. [ ] **بيانات الشركة**: معلومات التواصل، الدعم، العنوان القانوني المعتمدة للنشر العام.
6. [ ] بعد اعتماد كل ما سبق: مراجعة قانونية نهائية قبل الإطلاق العام.

## معايير الإتمام النهائية (Definition of Done)

المشروع "مكتمل" فعليًا فقط عندما تكون كل الصفوف التالية PASS مع دليل موثّق:

- [ ] كل الفجوات في المسار A مغلقة (لا PR معلّق، لا لوحة إدارة ناقصة معلنة كـ"فجوة مُفصح عنها" بلا سبب عمل وجيه لتأجيلها).
- [ ] عزل العملاء والمؤسسات مُتحقَّق منه حيًا على Staging، لا في الاختبارات الآلية فقط.
- [ ] نسخ احتياطي + استعادة مُختبَران فعليًا مع RPO/RTO مقاسين.
- [ ] مراقبة وتنبيهات حية مع مالك تشغيلي محدد.
- [ ] تمرين Rollback ناجح واحد على الأقل.
- [ ] قرار دفع/موردين نهائي ومُختبَر إن كان تكامليًا.
- [ ] موافقة قانونية/تجارية موثقة من المالك.
- [ ] Production Smoke Test حقيقي ناجح بعد النشر الفعلي.

عندها فقط يمكن تغيير التصنيف من **"NOT READY — EXTERNAL VERIFICATION REQUIRED"** إلى **"READY FOR PUBLIC PRODUCTION"**.
