# Staging deployment on Render

The repository-root `render.yaml` defines an isolated staging environment for
the `codex/nasaem-unified` branch. It intentionally does not modify the existing
`nasaem-platform` service.

## Resources

- `nasaem-platform-staging`: one Node web service in Frankfurt.
- `nasaem-platform-staging-db`: a private PostgreSQL 16 database in Frankfurt.
- `nasaem-staging-uploads`: a 1 GB persistent disk mounted at
  `/var/data/uploads`.

The web service serves both the API and the static frontend, applies committed
Prisma migrations before starting, and is checked through `GET /api/health`.
Uploads are stored only on the mounted persistent disk.

## First deployment

1. In Render, create a Blueprint from this repository and select `render.yaml`.
2. Review the paid service, database, and disk prices before applying it.
3. Supply a strong, unique `SEED_ADMIN_PASSWORD` when Render requests it.
4. Wait for the health check to pass.
5. Run `npm run prisma:seed` once from the staging service shell to create the
   initial administrator.
6. Sign in at `https://nasaem-platform-staging.onrender.com/login.html` and
   change the initial credentials according to the operating procedure.

`JWT_SECRET` is generated by Render. `DATABASE_URL` is connected to the private
database automatically. The database rejects public network connections.

## Release verification

Before promoting a commit to production:

1. Confirm `/api/health` returns HTTP 200.
2. Complete one customer request with multiple travelers.
3. Upload and download a document, redeploy the staging service, and confirm
   the same document is still available.
4. Verify staff login, order processing, payment recording, and deliverable
   download.
5. Review service and database metrics and error logs in Render.
6. Take a database recovery point and perform the documented restore drill on
   an isolated database before a production release.

Do not point automated tests at this database: backend tests delete and recreate
test data.
